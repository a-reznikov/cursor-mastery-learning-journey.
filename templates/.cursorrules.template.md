## Code Style & Conventions

### General Principles
- Write clean, readable, self-documenting code
- Prefer composition over inheritance
- Keep functions small and focused (< 20 lines when possible)
- Use descriptive variable names
- Add comments for "why", not "what"

### Language-Specific Rules

#### TypeScript
- ALWAYS use TypeScript, never plain JavaScript
- Use strict mode (`strict: true`)
- Prefer `interface` for object shapes
- Use type unions over enums when possible
- Avoid `any` - use `unknown` if type is truly unknown

```typescript
// ✅ Good
interface User {
  id: string;
  email: string;
  role: 'admin' | 'user' | 'guest';
}

// ❌ Bad
type User = any;
```

### File Organization

```
[Your project structure]
src/

│   ├── ui/              # Generic UI components
│   └── features/        # Feature-specific components
├── lib/                 # Utility functions
├── hooks/               # Custom React hooks
├── types/               # TypeScript types
└── __tests__/           # Tests
```

### Naming Conventions

- **Components:** PascalCase (`UserProfile.tsx`)
- **Hooks:** camelCase with "use" prefix (`useUserData.ts`)
- **Utilities:** camelCase (`formatDate.ts`)
- **Types:** PascalCase (`User`, `ApiResponse`)
- **Constants:** UPPER_SNAKE_CASE (`API_BASE_URL`)
- **Files:** Match primary export name

### Import Organization

Always organize imports in this order:

```typescript
// 1. External dependencies
import { useState, useEffect } from 'react';

// 2. Internal absolute imports
import { Button } from '@/components/ui/Button';

// 3. Relative imports
import { formatDate } from './utils';

// 4. Type imports (grouped separately)
import type { User } from '@/types';
```

## Testing Requirements

### Coverage Goals
- Unit tests: 80% minimum coverage
- Critical paths: 100% coverage
- All exported functions must have tests

### Testing Patterns

**Always test:**
- Happy path
- Edge cases
- Error conditions
- Boundary conditions

**Unit Test Example:**
```typescript
describe('calculateTotal', () => {
  it('should calculate total correctly', () => {
    expect(calculateTotal([10, 20, 30])).toBe(60);
  });
  
  it('should handle empty array', () => {
    expect(calculateTotal([])).toBe(0);
  });
  
  it('should throw error for invalid input', () => {
    expect(() => calculateTotal(null)).toThrow();
  });
});
```

## Error Handling

### Frontend
- Use Error Boundaries for component errors
- Display user-friendly error messages
- Log errors to monitoring service
- Never expose stack traces to users

```typescript
// ✅ Good
try {
  await api.updateUser(data);
  toast.success('Profile updated');
} catch (error) {
  logger.error('Failed to update user', error);
  toast.error('Failed to update profile. Please try again.');
}
```

### Backend
- Always validate input
- Return appropriate HTTP status codes
- Use custom error classes
- Log errors with context

## Security Rules

### Critical Security Requirements
- NEVER include actual API keys, passwords, or tokens in code
- NEVER commit .env files
- ALWAYS use environment variables for sensitive configuration
- Redact sensitive data before sharing with AI

### What's Safe to Share with AI
✅ Code structure and logic  
✅ Public API documentation  
✅ Error messages (redacted)  
✅ Test data (anonymized)  

### What's NOT Safe
❌ Production credentials  
❌ Real customer data  
❌ Internal production endpoints  
❌ Security vulnerability details (before patched)
